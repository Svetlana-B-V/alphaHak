# Бэкенд на пальцах: что происходит и почему

Этот файл — шпаргалка для тебя: что вообще делает бэкенд, как устроен код, что поменялось в последнем коммите и как отвечать на вопросы команды.

---

## 1. Большая картинка

Мы делаем **«Инсайт-Радар»**: сервис, который берёт поток новостей и говорит руководителям Яндекса, что из этого важно для их бизнеса и что делать (и какой продукт Альфа-Банка тут поможет).

Кто за что отвечает:

| Кто | Что делает | Что отдаёт другим |
|---|---|---|
| Аналитика | профиль Яндекса, сценарии, датасет новостей | JSON с новостями и профилем |
| ML 1 (RAG) | ChromaDB — поиск новостей **по смыслу** | релевантные новости |
| ML 2 (LLM) | промпты, оценка важности новости | инсайт в JSON: `event`, `impact`, `recommendation`, оценки |
| **Бэкенд (мы)** | хранит всё в БД и отдаёт через API | REST API для фронтенда |
| Фронтенд | дашборд в стиле Яндекса | то, что видит пользователь |

**Бэкенд — это «склад + окошко выдачи».** Склад — реляционная БД (новости, инсайты, лайки). Окошко — API: фронтенд стучится по адресу вида `/api/v1/news` и получает JSON.

Почему не хранить всё в ChromaDB? Chroma умеет только «найди похожее по смыслу». Хранить таблицы, связи, лайки, логи — это работа обычной БД (SQLite/PostgreSQL). Так и написано в нашем issue.

## 2. Словарик (коротко)

| Слово | Что это простыми словами |
|---|---|
| **API / эндпоинт** | адрес, по которому фронт что-то просит. `GET /api/v1/news` = «дай новости» |
| **GET / POST** | GET — «дай данные», POST — «вот тебе данные, прими» |
| **JSON** | формат обмена данными, похож на словарь Python |
| **FastAPI** | библиотека, на которой написан сервер |
| **Uvicorn** | программа, которая запускает сервер FastAPI |
| **Swagger (`/docs`)** | автоматическая страница с документацией всех эндпоинтов, где можно потыкать запросы |
| **SQLAlchemy / ORM** | работаем с таблицами БД как с классами Python, без ручного SQL |
| **Модель** (`models/`) | описание таблицы в БД: какие колонки, какие типы |
| **Alembic / миграция** | «история изменений» схемы БД. Каждое изменение таблиц — отдельный файл, который можно применить (`upgrade`) или откатить (`downgrade`). Как git, только для структуры БД |
| **Pydantic / схема** (`schemas/`) | описание формата JSON на входе и выходе. Проверяет, что прислали правильные данные |
| **Mock / заглушка** | ненастоящие данные, «манекен». Нужны, чтобы фронт мог работать, пока ML не готов |
| **CORS** | защита браузера: страница с сайта A не может обращаться к серверу B, если B явно не разрешил. Мы разрешаем только адреса нашего фронта |
| **`.env`** | локальный файл с настройками (адрес БД, адреса фронта). У каждого свой, в git не попадает |
| **Внешний ключ (FK)** | колонка-ссылка на другую таблицу. `insights.news_id` → «к какой новости относится вывод» |
| **CASCADE** | удалил новость → автоматически удалились её инсайты и лайки |
| **Индекс** | «оглавление» для колонки: поиск по ней работает быстрее |

## 3. Как проходит запрос (на примере ленты новостей)

Фронтенд открывает дашборд и запрашивает `GET /api/v1/news`:

```
Браузер (фронт)
   │  GET /api/v1/news
   ▼
main.py ─── CORS проверяет: запрос пришёл с разрешённого адреса фронта? да → пускаем
   │
   ▼
routers/news.py ─── «принимающий»: понимает, какой эндпоинт вызвали, и зовёт сервис
   │
   ▼
services/news.py ─── «мозг»: берёт данные (сейчас из mock_data.py), сортирует по важности
   │
   ▼
schemas/news.py ─── «контролёр формата»: проверяет, что ответ ровно такой, как обещали фронту
   │
   ▼
JSON уходит обратно во фронт
```

**Зачем столько слоёв?** Каждый слой делает одно дело. Главная выгода: когда заменим заглушки на настоящую БД и ML, поменяется **только `services/`**. Адреса и формат ответа останутся прежними, и фронтенду ничего переделывать не придётся.

## 4. Каждый файл — что внутри

```
app/
├── main.py         ← точка входа: создаёт приложение, включает CORS, подключает роутеры
├── config.py       ← читает настройки из .env (DATABASE_URL, CORS_ORIGINS)
├── database.py     ← подключение к БД + базовый класс для всех таблиц
├── models/         ← ТАБЛИЦЫ в БД
│   ├── news.py         новость
│   ├── insight.py      вывод ИИ по новости
│   └── feedback.py     лайк/дизлайк
├── schemas/        ← ФОРМАТ JSON (контракт с фронтом и ML)
│   ├── news.py         как выглядят новость и инсайт в ответе
│   └── feedback.py     что присылает фронт при лайке и что получает в ответ
├── routers/        ← ЭНДПОИНТЫ (адреса API)
│   ├── news.py         GET /api/v1/news, GET /api/v1/news/{id}
│   └── feedback.py     POST /api/v1/feedback
└── services/       ← ЛОГИКА
    ├── mock_data.py    заглушки: 3 новости про Яндекс с готовыми инсайтами
    ├── news.py         отдать список / одну новость
    ├── feedback.py     принять лайк (пока никуда не сохраняет)
    └── ai_agent.py     заглушка ИИ-агента: новость → инсайт (сюда ML вставит модель)

alembic/versions/   ← миграции БД (2 штуки)
tests/test_api.py   ← 9 автотестов API
```

### Модели vs схемы — в чём разница (частый вопрос)

- **Модель** (`models/`) — как данные лежат **в базе**.
- **Схема** (`schemas/`) — как данные выглядят **в JSON** снаружи.

Они похожи, но не одно и то же. Например, при лайке фронт не присылает `id` и `created_at` — их назначает сервер. Поэтому есть `FeedbackIn` (что приходит) и `FeedbackOut` (что уходит).

### Три таблицы

```
news (новость)
 ├── id, title, content
 ├── source        откуда: "РБК", "Интерфакс"...
 ├── source_url    ссылка (уникальная — одну новость дважды не загрузить)
 ├── published_at  когда вышла у источника
 └── created_at    когда попала к нам
      │
      │ 1 новость → много инсайтов
      ▼
insights (вывод ИИ)
 ├── news_id            → к какой новости
 ├── event              что произошло
 ├── impact             как влияет на Яндекс
 ├── recommendation     что делать
 ├── importance_score   важность 1..10 (1 = шум, 10 = критично)
 └── confidence_score   уверенность модели 0..1
      │
      ▼
feedback (лайк/дизлайк)
 ├── news_id       → какую новость оценили
 ├── insight_id    → (необязательно) какой именно вывод
 └── is_like       true = лайк, false = дизлайк
```

## 5. Что я поменял в последнем коммите и почему

Коммит `2b1b33a` в ветке `backend`. Здесь каждое изменение с обоснованием — на случай, если спросят.

### 5.1. Эндпоинты переехали из `main.py` в `routers/` и `services/`
- **Было:** всё лежало в `main.py`, а папки `routers/` и `services/` были пустыми.
- **Почему поменял:** в issue прямо требуется структура `routers / models / services`. Плюс заглушки теперь можно заменить на реальные данные, не трогая адреса API.

### 5.2. Добавлены Pydantic-схемы (`schemas/`)
- **Было:** `POST /feedback` принимал любой JSON. Я отправил `"is_like": "abc"` — сервер ответил «успех».
- **Стало:** неверный формат → ошибка `422`, несуществующая новость → `404`, успех → `201`.
- **Почему:** иначе мусор попадёт в БД, когда заглушку заменим на реальную запись. И в Swagger фронт теперь видит точный формат полей.

### 5.3. CORS теперь берёт адреса из настроек
- **Было:** `allow_origins=["*"]` — разрешено всем, а настройка `CORS_ORIGINS` из `.env` просто игнорировалась.
- **Стало:** разрешены только адреса фронта (`localhost:3000` и `localhost:5173` — это порт Vite).
- **Почему:** `*` вместе с `allow_credentials=True` — это дыра в безопасности, и браузеры такую комбинацию по стандарту не поддерживают. Если у фронта другой адрес — пусть добавит его в `CORS_ORIGINS` в своём `.env`.

### 5.4. Таблица `insights` переделана под ML 2
- **Было:** `text` + `risk_level`.
- **Стало:** `event`, `impact`, `recommendation`, `importance_score`, `confidence_score`.
- **Почему:** ровно эти поля ML 2 обещает возвращать по своему issue (#5): Event / Impact / Recommendation + скоринг 1–10 + confidence_score. Мы сохраняем их ответ как есть, без перекладывания.

### 5.5. В `news` добавлены `source`, `published_at`, уникальный `source_url`
- **Почему:** 15.10 бэкенд загружает датасет от аналитики. Дата публикации и источник пригодятся для ленты, а уникальная ссылка защищает от дублей при повторной загрузке.

### 5.6. Индексы и CASCADE на ссылках между таблицами
- Индексы ускоряют поиск «все инсайты этой новости».
- CASCADE: удалили новость — её инсайты и лайки удалились сами, «висящих» записей не остаётся.
- Для SQLite отдельно включил проверку внешних ключей (`PRAGMA foreign_keys=ON` в `database.py`). По умолчанию SQLite их **не проверяет**, это его особенность.

### 5.7. Вторая миграция пересоздаёт `insights` и `feedback`
- **Вопрос, который зададут: «Почему не исправил первую миграцию?»** Она уже была запушена. Правило: запушенные миграции не трогаем, иначе у тех, кто её уже применил, всё сломается. Поэтому сделал новую.
- **«Почему таблицы пересоздаются, а не меняются?»** В первой миграции внешние ключи создались без имён. Изменить ключ без имени Alembic не может, миграция просто падала. Таблицы были **пустые**, так что ничего не потерялось.
- Чтобы это не повторилось, в `database.py` добавил правило автоматического именования ключей и индексов (`naming_convention`).
- Проверено: `upgrade` и `downgrade` проходят в обе стороны и на существующей, и на новой БД.

### 5.8. Заглушки стали осмысленными
Три новости — это сценарии из issue аналитики:
1. **ЦБ снизил ставку** → долг Яндекса дешевеет → казначею: рефинансирование в Альфе (важность 8).
2. **Ужесточили закон о персональных данных** → регуляторный риск → CEO/CFO: резервы, страхование (важность 9).
3. **Вышел новый iPhone** → для Яндекса это шум (важность 1). Пример из issue ML 2: такие новости модель должна отсекать.

Лента сортируется по важности: самое критичное сверху.

### 5.9. Новый эндпоинт `GET /api/v1/news/{id}`
- **Почему:** по роадмапу 15.10 фронт верстает детальную карточку инсайта, ей нужна одна новость по id.

### 5.10. Тесты, чистка, мелочи
- `tests/test_api.py` — 7 тестов: Swagger открывается, лента отдаётся и отсортирована, валидация лайков работает, CORS пускает фронт и не пускает чужих.
- Удалил пустой `test.py` и ненужный `.gitkeep`.
- В `requirements.txt` закрепил версии последних трёх пакетов, чтобы у всех стояло одно и то же.
- `.mcp.json` (локальный конфиг PyCharm) добавил в `.gitignore`.
- Переписал `README_BACKEND.md` для всей команды.

### 5.11. Заглушка ИИ-агента (отдельный коммит после первого)
- **Что это:** `app/services/ai_agent.py` + эндпоинт `POST /api/v1/analyze`. Отправляешь текст новости — получаешь инсайт (`event`, `impact`, `recommendation`, оценки).
- **Как работает сейчас:** вместо LLM — правила по ключевым словам. «Ставка/ЦБ» → важность 8, «персональные данные» → 9, «санкции/серверы» → 7, всё остальное → шум (1).
- **Зачем:** это главная фича нашего трека (новость → персональный инсайт). ML пока не готов, но у фронта уже есть рабочий эндпоинт для демо, а у ML — понятное место для встраивания.
- **Что скажешь ML:** «Замените тело функции `analyze_news` в `ai_agent.py` на вызов вашей модели. На входе заголовок и текст, на выходе JSON из вашего же issue. Больше ничего менять не надо».

## 6. Вопросы от команды и что отвечать

**Фронт: «Что мне дёргать и в каком формате?»**
→ Открой `/docs` или раздел «Для фронтенда» в README. Формат финальный, данные пока заглушечные.

**Фронт: «У меня CORS-ошибка в браузере».**
→ Твой адрес не в списке разрешённых. Добавь его в `CORS_ORIGINS` в `.env` бэкенда и перезапусти сервер.

**ML: «Хотим добавить поле в инсайт (например, тип: риск/возможность)».**
→ Не проблема: добавлю поле в модель и схему и сделаю новую миграцию. Главное — сказать заранее.

**Кто угодно: «После пула всё упало / ошибка про таблицы».**
→ Выполни `alembic upgrade head`: пришла новая миграция.

**«Почему лайки не сохраняются?»**
→ Это заглушка по ТЗ Фазы 1 («эндпоинты возвращают заглушечные данные»). Сохранение в БД — следующий шаг.

**«Зачем SQLite, если есть PostgreSQL?»**
→ SQLite — для локальной разработки, ничего ставить не надо. На PostgreSQL переключаемся одной строкой `DATABASE_URL` в `.env`, код не меняется.

## 8. Шпаргалка команд

```powershell
.venv\Scripts\activate               # включить виртуальное окружение
uvicorn app.main:app --reload        # запустить сервер → http://127.0.0.1:8000/docs
pytest                               # прогнать тесты
alembic upgrade head                 # применить миграции
alembic current                      # какая версия БД сейчас
alembic revision --autogenerate -m "что поменял"   # новая миграция после правки моделей
```
